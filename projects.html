TurtleBot3 — Autonomous Navigation, SLAM & Localization

[ ROS2 · NAV2 · AMCL · SLAM · TF/ODOMETRY · GAZEBO/RVIZ ]

Built and validated a mobile-robot navigation workflow from robot bring-up and transforms through mapping, probabilistic localization, planner evaluation and simulation-to-real execution.

System flow: sensor/odometry inputs → TF tree → map generation → AMCL pose estimate → Nav2 global/local planning → velocity commands → closed-loop navigation checks.

Implementation: configured robot bring-up, TF and odometry, performed SLAM in simulation and on real hardware, used AMCL for localization and worked with Nav2 navigation behavior. Planner experiments included RRT, BiRRT and PRM comparisons alongside the navigation-stack work.

Validation focus: reproducible launch sequences, map/localization consistency, navigation behavior in RViz/Gazebo and transfer of validated workflows from simulation to the physical TurtleBot3.

Portfolio evidence to add: TF tree capture, saved map, RViz localization screenshot, Nav2 path visualization, planner-comparison plot/table and short sim-to-real navigation video.

UR10 Manipulator — Kinematics, Trajectory Planning & Control

[ MATLAB · SIMULINK/SIMSCAPE · ROS · KINEMATICS · DLS ]

Implemented manipulator-motion workflows around forward/inverse kinematics, damped least-squares control and ROS-compatible joint trajectories, then validated motion before hardware execution.

Core workflow: desired end-effector/task state → kinematic computation → joint configuration/vector conversion → trajectory generation → ROS JointTrajectory message → simulation/hardware execution.

Implementation detail: the project used helper functions for joint-name/index mapping and conversion between joint configurations and joint vectors, plus a trajectory-message conversion stage for ROS motion commands. Forward/inverse kinematics and DLS were used to reason about and control manipulator motion.

Validation: trajectories were checked in the simulation workflow before transfer to hardware experiments, reducing the risk of executing unverified joint commands directly on the robot.

Portfolio evidence to add: kinematic diagram, trajectory plot, MATLAB/Simulink screenshots, Gazebo/RViz motion sequence and short hardware demonstration.

IIoT Anomaly Detector — Edge-to-Cloud Monitoring

[ PYTHON · MQTT · ISOLATION FOREST · PLOTLY · SCIKIT-LEARN ]

Developed an MQTT-based industrial sensor pipeline that processed more than 5,000 datapoints, detected abnormal operating states with Isolation Forest and visualized trends with Plotly.

Architecture: sensor/data producer → MQTT transport → Python processing → feature/data handling → Isolation Forest inference → anomaly flagging → Plotly visualization.

Engineering focus: streaming telemetry rather than only offline CSV analysis, lightweight unsupervised detection for abnormal behavior, and readable visualization for inspecting measurements and trends.

Measured behavior: the project processed 5,000+ datapoints with sub-300 ms pipeline latency in the documented implementation.

Offline Guided Face Enrollment and Recognition

[ INSIGHTFACE · ONNX RUNTIME · OPENCV · PYTHON ]

Built an offline computer-vision pipeline for guided face enrollment and recognition with pose-aware input validation and low-latency video processing.

Pipeline: camera frame → face detection/alignment → pose/input-quality validation → embedding extraction → enrollment or similarity comparison → identity result.

Design choice: enrollment is guided rather than accepting every detected frame. Pose validation helps reject weak enrollment samples before they enter the stored identity representation.

Offline execution: InsightFace models are executed locally through ONNX Runtime and OpenCV handles image/video acquisition and processing, avoiding reliance on a cloud recognition API.

J&J MedTech — Robotics & Controls Troubleshooting

[ PYTHON · CONTROL CODE REVIEW · PERFORMANCE TESTING · DOCUMENTATION ]

Investigated a high-severity simulated robotic-control support ticket, reviewed command timing behavior, iteratively tested changes and documented findings and recommendations.

Ticket context: simulated Mercy General Hospital support case, robot model RBA-2201, ticket #2437, severity High, with rotate_joint identified as the affected command.

Initial timings: move_arm 0.104 s, rotate_joint 0.151 s, adjust_grip 0.063 s. After the exercise's optimization cycle: 0.083 s, 0.121 s and 0.041 s respectively.

Engineering workflow: reproduce ticket behavior → inspect Python control code → isolate likely bottleneck/logic path → modify/test iteratively → compare measured command timings → document steps, findings and recommendations.

Scope note: this is a completed J&J MedTech Forage job simulation and is presented as simulation experience, not employment at Johnson & Johnson.

SO-101 Robot Arm — Zero-Shot, Few-Shot & In-Context Learning for Pick-and-Place

[ SO-101 · ROBOT LEARNING · ZERO/FEW-SHOT · IN-CONTEXT LEARNING · PICK & PLACE ]

Ongoing project comparing learning strategies for robotic pick-and-place with a practical path from lightweight/offline experimentation to the physical SO-101 arm.

Current constraint: development targets a 16 GB RAM laptop with a GTX 1050 Ti 4 GB, so the workflow avoids depending on heavy Isaac Sim requirements and favors lightweight simulation/offline evaluation before hardware execution.

Experiment structure: define a common pick-and-place task and success criteria → establish a deterministic baseline → implement/evaluate zero-shot behavior → add a small number of demonstrations for few-shot comparison → test in-context conditioning → compare task success, execution consistency and failure modes.

Planned evidence: reproducible configs, task definitions, demonstration format, evaluation script, per-method results table, failure-case gallery and final hardware demonstration once validated.

Status rule: planned methods, milestones and expected outputs are intentionally not presented as completed results.
